# Phase 9: Automatic Session Title Generation

## Context

`ylva` is a Rust terminal AI-agent harness (TUI + headless CLI) with an
append-only JSONL session store (`src/store.rs`, blueprint §4H). Every
session file begins with a `meta` header line (`SessionMeta`, `src/store.rs`)
that carries a `title` field, currently populated by
`title_from_first_user_message` — a purely mechanical copy of the first
explicit user message (whitespace-flattened, truncated to `TITLE_MAX_CHARS`
= 80 chars). This is blueprint Phase 9's stated problem: titles should be
generated by a dedicated utility LLM call summarizing the exchange, not a
literal copy of the user's first message.

**Goal:** After a session's first conversation turn completes (first
explicit user message + first *completed* assistant reply), generate a
concise title via a separate, isolated "utility" LLM engine call and persist
it into the session's `meta.title` field, replacing the current copy-based
title derivation. Apply the same mechanism to resumed sessions with a still-
empty title, and to child-agent transcripts (using the child's first task
message and first reply).

**Acceptance criteria:**

- A new profile setting `utility_engine` (alongside `default_engine` and
  `compact_engine` in `ProfileConfig`, `src/config/profile.rs`) is resolved
  independently, falling back to `default_engine` when unset. Selecting or
  using it must never mutate the active conversation engine's runtime
  settings (model, temperature, etc.) or the `compact_engine`.
- Title generation is triggered exactly once per session, after the first
  turn's assistant reply reaches `AssistantStatus::Complete` (never for
  `Interrupted` replies, never for turns that never commit an explicit user
  message).
- The utility call runs as an explicit, temporary, single-shot conversation:
  no session store attached, no UI/`UiUpdate` traffic visible to the driver,
  no tools registered/offered.
- The utility prompt clearly delimits the first user message and first
  assistant reply and instructs the model to return only a bare title (no
  markdown, quotes, or explanation).
- The utility response is validated/normalized (single non-empty line,
  truncated to the existing title length limit). On failure (empty,
  malformed, multi-paragraph, or an engine error), the title is left empty
  for a later retry — it must never fall back to copying the user's message.
- The generated title is persisted via an explicit store operation that
  atomically rewrites only the `meta` header line (reusing the existing
  temp-file-plus-rename pattern), leaving all other lines untouched and in
  order.
- On `Store::resume`, a session whose first turn is complete but whose
  title is still empty re-triggers generation from the persisted
  transcript.
- Child transcripts (`Store::write_child_transcript`) get the same
  treatment, using the child's first task message and first reply.
- `docs/configuration.md`, `docs/persistence.md`, `docs/features.md`, and
  `docs/implementation-notes.md` are updated to describe the new mechanism,
  replacing the now-obsolete copy-based description.

**Key constraint — architectural mismatch to resolve first:** today, title
finalization happens *synchronously and entirely inside* `SessionWriter`
(`src/store.rs`), the dedicated writer task that owns the locked file
handle. `SessionWriter::append`/`finalize_title_if_pending` run with no
access to an `Engine`, no `tokio::spawn` of arbitrary async work tied to a
network call, and no knowledge of `ProfileConfig`/`AgentFactory`. Generating
a title via an LLM call is an inherently async, fallible, network-bound
operation that belongs at the driver layer (`ConsoleApp` in `src/cli_driver.rs`,
`TuiApp`/`AppState` in `src/tui_driver.rs`), which already owns the
`AgentFactory`, the active `ProfileConfig`, and the `Store` handle.

The resulting split (settled after review — see "Decisions locked in during
planning" below): `store.rs` owns *everything that is pure data/string
work and requires no network access* — detecting when a title is
generatable, and building the exact ready-to-send title-generation prompt
string from the transcript (`Store::title_prompt`). The driver layer owns
*everything that requires network access or session/process state* —
resolving the `utility_engine`, invoking `Engine::chat` with that prompt,
normalizing the response, deduplicating repeated attempts within one
process, and persisting the result back through `Store::set_title`. This
keeps `store.rs` fully synchronous and free of any `llm::engine` dependency,
while giving the driver one uniform entrypoint (`Store::title_prompt`) that
behaves identically whether the first turn just completed live or is being
retried after a resume.

**Decisions locked in during planning (do not revisit without cause):**

- `Store` owns building the full title-generation prompt string
  (`Store::title_prompt`), not just raw source strings — this keeps the
  prompt wording in one place and makes a future "regenerate from more than
  the first turn" feature a one-file change. Phase 9 ships this as a
  concrete, no-parameters method (YAGNI): it always reflects "first user
  message + first complete assistant reply". A future phase may generalize
  its signature once a concrete need for more context exists — this is an
  intentional extension point, not an oversight.
- Both the live-turn-just-completed path and the resume-retry path call the
  *same* `Store::title_prompt()` method — there is no separate "driver
  already has the text in hand" fast path. This avoids two parallel code
  paths for what is otherwise identical logic.
- The "already attempted in this process" dedup guard is owned by the
  driver (`ConsoleApp`/`TuiApp`/`AppState`), not by `Store` — this matches
  the existing one-process-per-session model and keeps `Store` free of
  engine-call bookkeeping.
- A malformed-but-recoverable utility reply (extra blank lines, a couple of
  extra lines, surrounding quote characters, over-length output) is
  **normalized then accepted** (first non-empty line, quotes stripped,
  truncated to `TITLE_MAX_CHARS`). Only a genuinely empty response or an
  engine/transport error is treated as a failure that leaves the title
  empty for a later retry.
- The driver's utility-title task is spawned off the agent-loop hot path. TUI
  work remains best-effort/detached, while the headless runner retains the
  started task handle until its visible run has finished so a normal CLI
  process can persist the generated title before exit. An interrupted or
  externally terminated process can still leave the title empty; the next
  `Store::resume` retries correctly.

## Implementation Plan

Flip each `[ ]` to `[x]` immediately after completing it and rewrite this
file in place, so progress is resumable across sessions.

1. [x] **Add `utility_engine` to `ProfileConfig`.** In
   `src/config/profile.rs`, add `pub utility_engine: Option<String>` next to
   `compact_engine` (same `#[serde(default)]` shape), default to `None` in
   `ProfileConfig::default()`, and add `utility_engine_name(&self) -> &str`
   mirroring `compact_engine_name` (falls back to `default_engine`). Update
   the `[engines.*]` existence check in `AgentFactory::from_profile`
   (`src/agent_factory.rs`, the `for required in [...]` loop) to also
   require `profile.utility_engine_name()` to name a configured engine.

2. [x] **Expose engine lookup by name from `AgentFactory`.** Add a method
   (e.g. `AgentFactory::engine(&self, name: &str) -> Option<Arc<dyn Engine>>`)
   returning the raw configured engine (not a router), so the driver layer
   can resolve the utility engine independently of the active
   conversation/compaction engine without constructing a new `EngineRouter`.

3. [x] **Redefine "turn complete" precisely, and capture the assistant side
   too.** In `src/store.rs`, change `SessionWriter::append`'s
   `turn_is_complete` check to require
   `Message::Assistant { status: AssistantStatus::Complete, .. }` (not any
   `Assistant` message), matching this plan's acceptance criteria and
   closing a gap in the existing (copy-based) implementation. Extend the
   writer's captured title-source state to also record the first such
   complete assistant reply's `content` (mirroring how
   `pending_title_source` already captures the first explicit user
   message), so both halves of the prompt are available together once the
   first turn completes.

4. [x] **Replace copy-based finalization with `Store::title_prompt()` /
   `Store::set_title()`.** Remove `title_from_first_user_message` and its
   call site in `finalize_title_if_pending`. In its place:
   - Add `Store::title_prompt(&self) -> Option<String>`: returns `None`
     until both the first explicit user message and the first complete
     assistant reply are known (live: captured by the writer as in step 3;
     resumed: re-derived from the on-disk transcript, see step 6); returns
     `Some(prompt)` where `prompt` is the fully-formed, ready-to-send
     title-generation prompt string — clearly delimited sections for the
     user message and the assistant reply, plus the instruction to return
     only a concise title with no explanation, markdown, or quotation
     marks. All prompt wording lives here, in one place.
   - Add `Store::set_title(&self, title: String) -> ...`: an async method
     that round-trips through the writer task (new channel message/command,
     analogous to how `flush_tx` already round-trips) and performs exactly
     one atomic `meta` rewrite via the existing `rewrite_meta_line`
     temp-file-plus-`rename()` pattern. Idempotent: a no-op once a
     non-empty title is already on disk.
   - `SessionWriter` itself no longer computes or decides on a title value —
     it only tracks readiness (`meta_awaiting_title`, the two captured
     source strings) and executes rewrites `Store::set_title` requests.

5. [x] **Trigger title generation from the driver layer.** In both
   `ConsoleApp` (`src/cli_driver.rs`) and `TuiApp`/`AppState`
   (`src/tui_driver.rs`), after observing the root agent loop's first
   completed turn (a `UiUpdate::StreamDone` — or equivalent terminal signal —
   whose preceding assistant message has `status: Complete`) **and** after
   attaching to a resumed `Store` whose on-disk title is still empty, call
   one shared helper that:
   - Uses a driver-owned "already attempted this session" guard (e.g. a
     `bool`/`HashSet<Uuid>` field alongside the driver's `Store` handle) so
     at most one attempt happens per process per session; a failed attempt
     is retried only by a later `Store::resume` (a new process), never
     re-attempted within the same running process.
   - Calls `store.title_prompt()`; skips entirely (no engine call) if it
     returns `None`.
   - Resolves `profile.utility_engine_name()` via the new
     `AgentFactory::engine` lookup from step 2, and calls `Engine::chat`
     directly with a single message built from the returned prompt string,
     an empty tool list, and a fresh `CancellationToken` — never through
     `AgentLoop`/`Context`, so no `UiUpdate`s are emitted and no session
     store is touched by this call itself.
   - Drains the returned `mpsc::Receiver<StreamEvent>` into one accumulated
     string, stopping cleanly on `StreamEvent::Done`/`Error`/`Cancelled`.
   - Normalizes the result: takes the first non-empty line, strips
     surrounding quote characters, truncates to `TITLE_MAX_CHARS` (reuse the
     constant from `src/store.rs`, make it `pub(crate)` if not already
     visible where needed). Only a genuinely empty response, or an
     engine/transport error, is treated as failure — in that case, do not
     call `Store::set_title`; leave the title empty for the next resume to
     retry.
   - On success (including the normalized-but-recovered cases above), calls
     `Store::set_title` (step 4) with the normalized title.
   - Runs this via `tokio::spawn`, off the hot path, so a slow or failing
     utility call never blocks the next user turn. This task is best-effort
     and detached: if the process exits before it completes, it is dropped
     without further handling (the next resume's retry covers that case).

6. [x] **Resume-time retry.** In `Store::resume` (`src/store.rs`), keep the
   existing detection of an empty on-disk title, but extend the
   re-derivation to also scan for the **first complete assistant reply**
   (extend `first_explicit_user_message`'s sibling logic, or add a
   `first_complete_assistant_reply` scan), so `Store::title_prompt()`
   returns `Some(...)` immediately after resume whenever both messages are
   already in the transcript — the driver layer then calls the exact same
   shared helper from step 5, without waiting for a brand-new turn.

7. [x] **Child transcript titles.** Wire the same driver-level helper
   (step 5) into child-agent completion handling (`ChildAgentManager` /
   `src/agent/child_agent_manager.rs` and wherever
   `Store::write_child_transcript` is invoked), triggered live, right when
   the child's run completes (not deferred to lazy transcript loading),
   using the child's own `Store` handle so `title_prompt()` reflects the
   child's first task message and first reply.

8. [x] **Tests.**
   - `src/store.rs`: unit tests for the tightened `turn_is_complete` check
     (an `Interrupted` assistant message must not trigger title-readiness),
     for `Store::title_prompt` (returns `None` until both source messages
     are known; exact prompt content/delimiters once both are known; same
     behavior whether the state came from a live turn or from
     `Store::resume`'s re-derivation), and for `Store::set_title` (atomic
     rewrite, idempotent no-op once already set, correctness of bytes after
     the rewrite point).
   - `src/config/profile.rs`: unit tests for `utility_engine_name` falling
     back to `default_engine`, and for `AgentFactory::from_profile` failing
     when `utility_engine` names an engine absent from `[engines.*]`.
   - `src/cli_driver.rs` / `src/tui_driver.rs`: seam-level tests using the
     existing `StubEngine` test-double pattern (`src/tui_driver.rs`) —
     extend or add a stub utility engine to assert: the exact prompt sent
     for title generation matches `Store::title_prompt()`'s output; the
     utility call never emits `UiUpdate`s visible to the TUI/CLI rendering
     path; a malformed-but-recoverable reply (extra lines, quotes,
     over-length) is normalized and accepted; a genuinely empty or
     engine-error reply leaves the title empty rather than falling back to
     the user's message; a successful reply results in exactly one `meta`
     rewrite; and the driver-owned guard prevents a second attempt within
     the same process once one has already run.
   - Add or extend a `tests/*.rs` integration test (see existing
     `store_persistence_e2e` pattern, `docs/development-workflow.md`) that
     drives a full headless turn against a stub/fake provider and asserts
     the persisted `meta.title` on disk was produced by the utility path
     (not a literal copy of the first user message).

9. [x] **Documentation.**
   - `docs/configuration.md`: document the new `utility_engine` setting in
     both configuration tables (mirroring the existing `compact_engine`
     rows at lines ~82 and ~155), and update the `[engines.*]` "hard error"
     note to include `utility_engine`.
   - `docs/persistence.md`: replace the `title` field description (around
     line 84) and the "Immediate `meta` header, deferred title" narrative
     (around lines 88–100) to describe utility-engine-based generation,
     validation/normalization, the failure-leaves-title-empty behavior, and
     the resume-retry path — removing the now-inaccurate "copied from first
     user message" description.
   - `docs/implementation-notes.md`: replace the "Immediate `meta` header,
     deferred title" implementation note (around lines 292–302) with the
     new split between `SessionWriter`'s synchronous detection and the
     driver layer's async utility-engine call plus `Store::set_title`.
   - `docs/features.md`: add/update the user-facing note that session
     titles are LLM-generated summaries rather than a copy of the user's

   - `docs/blueprint.md`: flip Phase 9's checkboxes (§7, "Phase 9: Automatic

## Proposed Improvements

- Consider exposing a manual `/rename` or `/title` slash command as a
  follow-up (not required by this phase) so a user can override or force a
  regeneration of a title that the utility engine produced poorly — useful
  since a bad LLM title is otherwise sticky (once non-empty, `set_title`
  becomes a no-op per this plan's idempotency requirement).
- Consider logging (`tracing::warn!`) every utility-title failure (empty/
  malformed response, engine error) with the session id, to make the
  "left pending for a later retry" behavior observable in day-to-day use
  without needing to inspect the JSONL file directly.

## Consistency Issues

- [high] The current implementation performs title finalization entirely
  inside `SessionWriter`'s synchronous `run_writer` loop
  (`src/store.rs`), which has no access to `Engine`/`AgentFactory` and runs
  on every event append. Introducing an LLM call at this point would either
  block the writer task on network I/O (starving the append/flush loop for
  every other event) or require plumbing async engine access into
  `store.rs`, which would break `store.rs`'s current independence from
  `llm::engine` (checked: `src/store.rs` does not import
  `crate::llm` today). This plan resolves the conflict by keeping
  `store.rs` responsible only for *detecting* readiness and *building the
  prompt string* (`Store::title_prompt`, pure data/string work, no network),
  plus *persisting* a given title string (`Store::set_title`), while moving
  the actual utility-engine call to the driver layer, which already depends
  on both `Store` and `Engine`. Any implementation that instead tries to
  make `SessionWriter` call an engine directly must be treated as
  contradicting this boundary and revisited.

## Implementation Hints

- `src/store.rs`: `TITLE_MAX_CHARS = 80`; `title_from_first_user_message`
  (to be removed, replaced by `Store::title_prompt`); `SessionWriter::append`,
  `finalize_title_if_pending`, `rewrite_meta_line` (atomic temp-file +
  `rename()` pattern to reuse for `Store::set_title`); `first_explicit_user_message`
  (transcript scan pattern to mirror for the first complete assistant
  reply); `Store::create`, `Store::resume`, `Store::start_new_session_with_id`
  all construct `TitleState`/`meta_awaiting_title` — `Store::title_prompt`
  must behave consistently regardless of which of these three constructed
  the current `TitleState`.
- `src/config/profile.rs`: `ProfileConfig::compact_engine` /
  `compact_engine_name` (lines ~41, ~93, ~228–233) is the exact pattern to
  mirror for `utility_engine`; note its own doc comment already says
  "Phase 10 wires this at runtime" — `compact_engine` is itself still
  unused beyond validation, so `utility_engine` will be the first of the
  three profile-level engine slots actually invoked at runtime.
- `src/agent_factory.rs`: `AgentFactory::from_profile` (~line 79) builds
  the `engines: HashMap<String, Arc<dyn Engine>>` and validates
  `default_engine`/`compact_engine_name` exist (~line 135); `AgentFactory::build`
  (~line 237) shows how a named engine is resolved and wrapped in
  `EngineRouter` only when more than one engine is configured — a utility
  call should use the raw named engine directly, not a router, since it
  must not follow `/models` engine-switching behavior.
- `src/llm/engine.rs`: `Engine::chat` (trait, ~line 249) is the seam to
  call directly for a one-shot utility request:
  `fn chat<'a>(&'a self, messages: Vec<Message>, tools: Vec<ToolSchema>,`
  `cancel: CancellationToken) -> BoxFuture<'a, anyhow::Result<mpsc::Receiver<StreamEvent>>>`.
  Pass `tools: vec![]` for "no tools". `StreamEvent` (in `src/agent.rs`,
  ~line 328) has variants `Text`, `Thinking`, `Delta`, `Done`, `Cancelled`,
  `Error` — accumulate `Text`/`Delta` content until `Done`.
- `src/agent.rs`: `AssistantStatus` (~line 343) has `Complete` and
  `Interrupted` variants; `Message::Assistant { content, status, tool_calls }`
  (~line 430). `UiUpdate` (~line 151) is the channel drivers already
  consume; `StreamDone` is the existing terminal-stream signal to hook
  post-turn logic on.
- `src/tui_driver.rs` (~line 2332): existing `StubEngine` test double
  implementing `Engine` for TUI seam tests — the pattern to extend for a
  test double that returns a scripted utility-title response.
- `docs/configuration.md` lines ~82 and ~155 document `compact_engine`
  today; `docs/persistence.md` lines 58, 70, 84, 88–100, 240 and
  `docs/implementation-notes.md` lines 292–302 document the current
  copy-based title mechanism and must be rewritten, not merely appended to.
